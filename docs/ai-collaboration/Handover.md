### In-app Notification Triggers (Sep 3 — FEATURE-33 / D-58)
- `notifyUser(userId, message, type, { link })` from `src/lib/notify.ts` is the single entry point for `private-user-{userId}` Pusher events. It persists a `Notification` row first (DB-level idempotency on `_id`), then triggers Pusher. The bell inbox panel reads from `GET /api/notifications`; the transient toast comes from the existing `NotificationProvider`. Both the persisted row and the toast are produced by the same `notifyUser` call.
- The following 9 state-change points now call `notifyUser` (all fire-and-forget, `void notifyUser(...)`):
  - **Item 1** — `PATCH /api/admin/jobs/[id]/resolve` (dispute outcome + optional payout-status).
  - **Item 2** — `POST /api/jobs/[id]/accept` (driver → poster).
  - **Item 3** — `POST /api/jobs/[id]/deliver` (driver → poster).
  - **Item 4** — `POST /api/jobs/[id]/transit` (driver → poster).
  - **Item 5** — `GET /api/payments/khalti/verify` (poster success/failure + driver payout initiated).
  - **Item 6** — `GET /api/payments/esewa/verify` (poster success/failure + driver payout initiated).
  - **Item 8** — `POST /api/jobs/[id]/messages` (other participant).
  - **Item 9** — `POST /api/jobs/[id]/admin-message` (admin → participant).
  - **Item 11** — `PATCH /api/admin/payouts/[id]` (admin → driver).
- Types used: `success` for positive events (delivery complete, payment received, payout paid), `info` for state changes (transit, accept, message, dispute outcome), `error` for failures (payment failed/cancelled/refunded, payout failed).
- Every `notifyUser` call passes a `{ link }` so the bell inbox item is a real deep-link back to the relevant page (`/jobs/{id}` for state changes, `/driver/payouts` for payout events). The existing `Notification` model already stores the link field (FEATURE-24); this is the first feature to actually populate it.
- Why `void notifyUser(...)` not `await` + `.catch()`: the field guide says "Fire-and-forget is the established pattern for non-critical side effects — never block a live response on them, and always .catch()." `notifyUser` already has its own try/catch around `Notification.create` and the Pusher trigger, so an external `.catch()` would be dead code. Using `void` is the most accurate way to express "we deliberately don't await this" and satisfies ESLint's `no-floating-promises` rule.

## 🚫 Avoid / Don't Repeat

- **Never invent a job status.** The `JOB_STATUS` enum is fixed: `posted | accepted | in_transit | delivered | cancelled`. There is **no `completed`** — use `JOB_STATUS.DELIVERED`.
- **Never fetch all records** — pagination from day one, `PAGE_SIZE = 10` (jobs), 10 (reviews), 50/100 cap (messages).
- **Never introduce a new dependency without asking first** (strict constraint).
- **Never mix icon libraries** — Material Symbols Outlined only.
- **Never skip the Mongoose HMR guard** — `mongoose.models.X || mongoose.model("X", schema)` or you'll get `OverwriteModelError`.
- **Never pass `refreshTokenHash` or `passwordHash` in API responses.**
- **Never accept a change you can't explain in your own words** (Habit 15).
